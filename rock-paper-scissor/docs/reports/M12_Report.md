## Departure arbitration contract

Existing M11 finalization accepts a frozen departure list. If a peer leaves after finalization is sent but before its transaction commits, a pending status read cannot cancel/arbitrate the earlier in-flight write. Treating final card lock as the no-forfeit boundary would weaken the approved server commitment rule. This was surfaced to the creator; creator approves (“sure sure”) backend departure arbitration serialized against commitment. It is now implemented through authenticated POST `/api/matches/result`: a transaction records the departure only while uncommitted; finalization serializes against that write, merges server-held departure facts, and commitment remains immutable. Client status/retries preserve history identity and resolve pending departure facts before delivery. Ordinary host/non-host observations remain required. Typecheck and affected-script checks pass; source inspection alone is not evidence for the required ordinary departure checks.
