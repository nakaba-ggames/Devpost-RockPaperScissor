## Identity, authority, timing and messages

A match is offered only after both SDK peer IDs have bound preview participant snapshots in the actual queue lobby. The host creates one random canonical match ID, immutable actor IDs, rules revision, condition and shuffled starting orders. Each view maps its local actor below and opponent above; canonical actor/history identity stays unchanged. A relay switch can assign a new client ID: publish the profile using the ID read at `lobby_joined`, not a pre-queue ID.

The lobby closes when two profiles bind. Offer/ACK/reservation messages retain one pending/committed context; a bounded Resource-owned retry handles host-assignment notification arriving after an offer. Ingress rejects offers from an unrecognized host or different lobby. Search cancellation invalidates the generation before awaiting the SDK. A late callback cannot commit both human and fallback reservations. Cancellation-at-arrival injection is deferred, not passed.

Wire envelope: `{matchId, phase, actorId, sequence, revision, payload}`. Only one session ingress is exposed at the stable scene path. Match identity, actual sender membership/opponent binding and monotonic sender sequence gate packets. Decisions additionally require the current phase, expected actor, increasing actor/phase revision and an unexpired host deadline. The host orders accepted/defaulted events. State revisions are monotonic. The approved trusted-host tradeoff remains: no backend referee or cheat detection.

Only the current host locks phases and executes bots. UI readiness from each connected human precedes host phase start; both decisions never shorten the 15-second window. Deadlines are in canonical **match-elapsed** milliseconds. A follower estimates translation using its own echoed ping/round-trip midpoint plus host elapsed time; it never compares raw monotonic ticks from unrelated processes. On host departure, the survivor adopts that translated epoch and retains the deadline. Presentation tweens do not lock phases or determine deadlines.

Accepted snapshots retain starting order, actual initial/final cards, identity/switch claims, per-phase default/lock facts, events, phase/deadline, accepted revisions, control/departure status and rules revision. Hidden fields exist in peer memory under the approved continuation tradeoff, never as face-up choices in ordinary UI or as the opponent's hidden input to bot policy. No reconnect, grace period, resume ticket or rejoining protocol exists.

On a pre-ACK peer departure, the survivor retains the displayed identity and accepted history; that side becomes takeover-controlled and ineligible. Already accepted human choices in the current window are retained; empty/future phases use the Resource policy. A locally disconnected client stops authority/credit and can return without resuming. Connected inactivity uses ordinary defaults.

## Development acknowledgement and provider boundaries

The host freezes one structured result/history and stable `matchId:result` identity. Both peers retain the matching deterministic simulated receipt. The receiving peer acknowledges after retaining the result/receipt; it can consume that cached receipt even if the host leaves before echoing the commit. The host gates its receipt on that readiness response, then publishes/installs the same receipt. Bot-only continuation acknowledges locally. A post-ACK departure cannot rewrite that retained submission or its eligibility.

This is a **live peer-memory development acknowledgement**, not real server commitment, distributed durable storage, atomic settlement under connection loss, or restart-safe recovery. The normal protocol retains data on both peers before presentation; the narrow uncertainty window around an ACK in flight is part of the deferred race/error verification, not a claim of backend guarantees. M12 must replace this with the approved independently queryable backend commitment.

Receipts explicitly retain `simulated=true`, `serverAcknowledged=false`, `persisted=false`, `persistentCreditAllowed=false`. Each client applies the same eligible acknowledged event through the existing once-only preview provider. Quest IDs are captured synchronously before local choice play; no snapshot/history replay starts a newly active quest. Departed humans and takeover sides receive no match-derived updates. Ordinary fallback bot recipients remain eligible in the frozen envelope, but no backend bot profile is persisted. Names/IDs are local previews; points/stats/history/quests/receipts remain session-only development data. No fixture upload or backend work.

Chat uses actual peer transport/host acceptance and actor sequences through the existing overlay seam. Plain Label text, frontmost input blocking, clock continuation, cinematic opening gate/automatic closure and disposal remain. Bots never reply; no archive or storage is added.
